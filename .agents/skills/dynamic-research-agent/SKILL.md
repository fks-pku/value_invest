# Dynamic Research Agent

把研究看成一棵边执行边生长的问题树，而不是一开始设计完整目录。

用户只需要提出一个 L1 元问题。研究 agent 负责逐层拆解、逐题取证、形成结论，
并根据答案是否充分决定停止当前分支，还是继续向下一层展开。

## 核心原则

1. **问题驱动**：每次搜集数据都服务于一个明确的当前问题。
2. **边研究边展开**：只生成回答当前父问题所必需的下一层子问题，不预先生成整棵树。
3. **逐子问题闭环**：每个子问题都经历“搜集数据 → 分析 → 结论 → 充分性判断”。
4. **缺口触发下钻**：只有答案不充分，而且能够说清缺少什么时，才继续展开。
5. **父问题由子结论汇总**：不能用未经验证的背景知识替代子问题结论。
6. **全程可追溯**：保留问题、来源、分析、结论、充分性判断和下钻原因。
7. **第一性原理，问题简洁**：先建立必要的对象认知，再从关键变量和约束解释影响；保留有助于理解对象或改变父判断的问题，不用术语或目录完整性代替思考。

## 问题设计：研究对象 → 行业与 BOM 影响 → 具体公司

完整的行业、技术或事件投资研究，L1 下的上层主线固定为：
**这是啥（研究对象）→ 影响啥（行业与 BOM）→ 具体看谁（公司与投资价值）**。
这既是阅读顺序，也是判断的依赖关系。不要把“采用、付费、利润”等分析变量直接
代替这三个上层部分，也不要让假说清单、方法步骤或抽象因果链成为报告目录。

用户只研究一个环节、一个节点或一家公司的特定问题时，保留该范围，不为凑三部分
扩大任务。既有 standalone-BOM 五视角、行业索引和六问题报告契约不自动改版；
本规则用于完整研究的问题架构，不替代各报告的既有展示契约。

### 1. 先认识研究对象

先说明是什么、背景与定位、相对既有方案改变了什么，再分别研究技术/产品特性与
成本经济性。背景是读者理解后续影响的必要基础，不能全部降为不重要的附录；
但只保留有助于理解机制的背景，不写无关百科。

按对象选择下层问题：模型可研究技术能力和成本，政策可研究条款与适用范围，
产品可研究性能、用途与交付条件，不把 GPT-6 的技术/成本子目录套给所有对象。
区分已知事实、厂商声明、实测结果和未知信息；未公开的架构、训练成本不得猜成事实。
客户支付价格、完成任务的总成本、厂商生产/服务成本分别核算，不能互相替代。

事件研究先核实发布时间、实际可用范围和限制；未核实时保留待验证前提或情景性质。
统一证据截止日，并明确上一代、可采购替代方案与无事件路径，不能把既有增长全算作事件增量。

### 2. 再解释行业与 BOM 影响

先画清研究对象所在的产业链和边界，默认按上游、中游、下游拆影响；
若对象更适合其它影响维度，说明依据，不机械套硬件产业链。
沿用项目 canonical BOM ID 与名称，不另造同义节点。一家公司跨多个环节时按业务拆分。

每个环节内部按第一性原理解释：
**对象的哪项变化 → 改变本环节什么变量 → 通过什么机制 → 方向、规模、时间及失效条件**。

需求、供给、成本、竞争、利润是按需要选用的分析维度，不是在每个环节下必填的重复目录。
例如上游可能重点看资源消耗与供需，下游重点看付费任务和替代；不要对上中下游机械复制同一组题。
BOM 节点只在该环节取证后暴露具体缺口时继续下钻，不预列 GPU、HBM、网络等全部深层子树。
完整行业链正式执行仍遵守 canonical BOM 注册、逐节点研究与投资门禁。

区分技术可行、实际采用、付费需求、资源用量、采购及利润；任意一项变化都不自动证明下一项。
需求须有当前基线，未来变化区分新增、替代和提前兑现。对重要机制同时检验无变化或相反解释。
不得从“模型更强”直接跳到“硬件受益”，也不得把技术声明当作规模化采用的证明。

### 3. 最后落实到具体公司

候选公司来自第二部分已识别的受影响环节，既包括可能受益者，也包括可能受损者。
先核实公司业务敞口，不按热门股票或已有材料倒推产业逻辑。尚不能识别具体公司时，
保留明确的公司筛选问题及数据要求；不虚构公司 A/B 作为已经创建、可执行的研究节点。

对象确定后，按公司组织独立节点，而不是只写一篇泛化的“行业盈利与估值”。
每家公司解释业务关联、竞争优势、收入/利润/现金流传导、市场已计入的预期，以及反证和风险。
这些是本公司需要回答的内容，未取证前不自动拆成固定 L4/L5。
行业利好不等于公司利好，公司利好不等于证券值得买；需要投资建议时仍须通过
稀缺性、错误定价、盈利弹性和风险控制等门禁。仅要求行业判断时，不擅自扩大到买卖建议。

### 4. 在稳定主线内设计简洁问题

初始正式计划到必要的 L1/L2/L3，各当前叶子都写所需数据与分析；不预生成 L4/L5。
先尝试取证，只有具体缺口需要拆解时才下钻一层，最多 L5。
三部分是上层结构，不意味着每部分必须有相同数量的子问题。

每个拟保留的问题说明四件事：

| 审查项 | 必须说清楚 |
| --- | --- |
| 用途 | 它提供哪项必要的对象认知，或改变哪个影响/公司判断？ |
| 对照 | 研究对象、期间、替代方案和基线是什么？ |
| 证据 | 需要什么数据、怎样分析、什么结果会反驳当前解释？ |
| 父子关系 | 子结论怎样共同回答父问题，是否还缺关键环节？ |

第一性原理体现在节点内的推理，不是将上层标题写得抽象复杂。
每题尽量只问一件事，问句用人话；指标、公式、样本和验收口径放在数据/分析要求。
小样本不能代替整个行业。相同事实跨节点使用仍需逐题抽取和复核；依赖关系不等于错误嵌套。

正式取证前检查三部分是否连贯、范围是否恰当、是否遗漏必要环节或重复采集。
审查只记录“可执行 / 需重设计”及理由，不把设计通过当作研究完成。
优先完成对象认知，再研究影响和公司；执行中可按依赖、判断重要性和可查清程度调整顺序。
若用户只要求设计或更新 skill，到设计审查即止，不自动搜索、改报告或启动研究。

### 5. 未答充分时，先判断原因

- 缺少某项数据：补证或明确阻塞，不增加层级。
- 问题混合多个机制：记录缺口，展开最少的下一层问题。
- 证据冲突：先核对口径与替代解释。
- 子题已答但父题仍无法判断：补同层遗漏、合并或调整归属，不只会向下钻。
- 依赖未来事件：给条件判断与验证指标，不强求确定答案。

修订问题范围或选择具体公司时保留旧版本及理由，重新评估证据适用性，不自动继承通过状态。

### 示例：GPT-6 发布影响

以下只示范初始框架，不表示已核实发布或完成研究。

- L1：GPT-6 发布对 AI 行业及相关公司有什么影响？
  - L2：研究对象是什么，发生了什么变化？
    - L3：GPT-6 是什么，背景与定位是什么？
    - L3：GPT-6 的技术特性与能力边界怎样变化？
    - L3：GPT-6 的成本与使用经济性怎样变化？
  - L2：怎样影响行业和 BOM？
    - L3：怎样影响上游算力与基础设施？
    - L3：怎样影响中游模型与服务平台？
    - L3：怎样影响下游应用与最终需求？
  - L2：具体公司有哪些投资机会或风险？
    - L3：哪些公司具有可验证的业务敞口，值得进一步研究？

示例中上游指硬件与基础设施，中游指模型与服务平台，下游指应用及最终客户；
云业务须区分基础设施采购与模型服务，不能重复归集同一收入或支出。
初始公司筛选题并非完整公司研究：筛选完成后若父题仍缺公司级证据，追加真实的
逐公司 L3 节点及执行契约；保留筛选记录，不改写旧问题 ID，不预建虚构公司或整套 L4/L5。
技术与成本两题分别取证；实际客户需求归下游，需求传向资源采购的影响归上游，
公司盈利与定价归具体公司，节点间引用已验证结论而非互相替代证据。

## 输入

启动研究时至少确认：

- `L1 元问题`：用户最终想知道什么。
- `研究边界`：对象、时间、地区、口径；用户没有给出时，采用最保守的明确假设。
- `完成标准`：什么样的答案足以支持用户的决策。
- `最大深度`：默认到 L5；到达 L5 仍不能回答时，记录为阻塞，不编造结论。

不要要求用户先设计 L2、L3。层级展开是 agent 的职责。

## 节点模型

问题树中的每个节点都使用同一结构：

```yaml
question_id: 稳定的问题编号
level: L1-L5
parent_id: 父问题编号；L1 为空
question: 这个节点要回答什么
why_it_matters: 它如何帮助回答父问题
status: pending | researching | answered | expanded | blocked
children: 已实际创建的直接子问题
conclusion: 当前结论
sufficiency:
  passed: true | false
  reasons: 为什么充分或不充分
  gaps: 仍缺少哪些证据、口径、对象或机制
```

每个当前终端节点还要保存：

```yaml
data_required: 需要搜集的数据
sources: 实际使用的来源及原文定位
analysis: 基于数据做了什么分析
supporting_evidence: 支持结论的证据
contrary_evidence: 反向证据或适用边界
next_action: 结束、继续搜集，或创建下一层子问题
```

## 研究循环

### 第一步：定义当前层要回答什么

对当前父节点明确写出：

- 本层问题。
- 它的回答边界。
- 什么结果算回答充分。

问题必须可以被证据回答，不能只是“了解一下”“分析行业”等宽泛表述。

### 第二步：生成最少量的直接子问题

先按“问题设计”完成逐题及整组审查，再列出回答当前节点所必需的直接子问题。每个子问题应当：

- 独立回答一个事实、比较、因果机制或反证。
- 能够通过具体数据或材料验证。
- 回答后可以直接贡献给父节点。
- 不与兄弟问题重复。

除仓库正式启动时建立必要的 L1/L2/L3 外，每次只展开一层；不预生成 L4/L5，
也不要为了形式完整强行凑固定数量。

如果当前节点本身已经足够具体，可以直接研究它，不必机械拆分。

### 第三步：逐个研究子问题

对每一个当前终端子问题，严格执行以下闭环。

#### 3.1 收集数据

- 先写明需要哪些数据，再开始搜索。
- 每次搜索绑定当前问题编号。
- 优先使用原始资料、官方数据和可复核材料。
- 同时寻找支持材料与反向材料。
- 记录来源、发布日期、事实所属期间、口径和原文位置。
- 宽泛材料池只能提供候选，不能批量映射成多个问题的完成证据。
- 同一来源用于不同问题时，分别抽取和复核。

#### 3.2 做出分析

- 区分事实、推断和判断。
- 统一对象、单位、期间和统计口径。
- 解释数据如何回答当前问题，而不是只摘要材料。
- 比较支持证据、反向证据和替代解释。
- 明确不确定性来自数据缺失、口径冲突，还是机制尚未验证。

#### 3.3 得到结论

结论只回答当前子问题，至少包含：

- 一句话答案。
- 支持答案的关键证据。
- 反向证据或适用边界。
- 尚未解决的缺口。

没有证据支持的内容写成假设，不写成事实。

#### 3.4 判断回答是否充分

使用通过/不通过判断，不使用模糊的置信度分数。

只有同时满足以下条件，当前节点才算充分：

- 结论直接回答了问题。
- 核心事实具有可追溯来源。
- 对象、期间和口径足以支撑比较。
- 关键反向证据已经搜索并处理。
- 剩余缺口不会实质改变父问题的答案。

如果通过：

- 将节点标记为 `answered`。
- 停止该分支，不再增加层级。

如果不通过：

- 继续补证时保留 `researching`；实际新增子问题才标记 `expanded`，无法推进时标记 `blocked`。
- 先写出具体缺口，例如“缺少 A 客户的当前部署数据”，而不是“资料不足”。
- 先按缺口类型选择补证、核对矛盾、修订同层问题、条件判断或下钻；不把缺数据自动转为子问题。
- 确需下钻时，仅创建最少量的下一层问题，逐题指明所关闭的缺口，并重复第三步。

### 第四步：汇总父节点

当所有必要子问题都已回答后：

1. 汇总子问题结论，形成父节点结论。
2. 再次判断父节点是否回答充分。
3. 若充分，关闭父节点并向上一层汇总。
4. 若仍不充分，识别缺口，选择补证、处理矛盾或版本化修订；仅必要时新增直接子问题。

父节点不能因为“所有子问题都跑过”而自动完成；完成取决于答案是否充分。

## 循环伪代码

```text
research(node):
    明确 node 要回答什么，以及充分条件

    if node 足够具体且尚未研究:
        搜集数据(node)
        分析(node)
        形成结论(node)
        判断充分性(node)

    if node 回答充分:
        关闭 node
        return node.conclusion

    记录具体缺口

    若仅缺数据或口径冲突：补证或核对后重新判断；通过则返回结论，仍不可得则记录 blocked 并返回
    若依赖未来事件：记录条件判断、未解决缺口与下一验证，不标记充分，并返回
    若拆分逻辑有误：版本化修订同层问题及依赖

    if node.level == L5 and 缺口仍需下钻:
        标记 blocked
        return 未解决缺口

    仅在确需下钻时按缺口创建下一层必要子问题

    for child in node.children:
        research(child)

    用子结论重新回答 node
    再次判断 node 是否充分
```

## 动态更新规则

每发生一个动作就追加一条事件，不覆盖历史：

- `question_created`
- `collection_started`
- `source_attached`
- `analysis_recorded`
- `conclusion_recorded`
- `sufficiency_evaluated`
- `question_expanded`
- `question_closed`
- `question_blocked`

动态计划展示的是事件账本投影出的当前状态。修改结论时保留旧结论及修改原因。

如果在文件型工作区运行，使用三个最小工件：

- `research_plan.md`：给人看的当前问题树和执行位置。
- `research_state.json`：当前节点、父子关系和充分性状态。
- `research_events.jsonl`：追加式事件与证据追踪。

不要为了归档方便再复制一套结论；结论只在状态和事件中有一个来源。

## 每轮输出格式

以下是内部执行记录或用户要求工作台时的格式，不是公共报告的文章模板。
普通汇报先给答案、关键依据及下一步；正式报告遵守下文的文章化要求。

```markdown
## 当前研究节点

- 层级与问题：L[n] · [问题]
- 父问题：[父问题]

### 数据

- [来源与关键事实]

### 分析

- [事实如何回答当前问题]
- [反向证据或边界]

### 结论

[只回答当前问题的一句话结论]

### 充分性判断

- 结果：通过 / 不通过
- 理由：[具体理由]
- 缺口：[具体缺口；没有则写“无重大缺口”]

### 动态计划更新

- 通过：关闭当前分支，返回父节点汇总。
- 不通过：新增 L[n+1] 子问题：[问题及其对应缺口]。
- 下一步：[唯一的下一执行节点]
```

## 研究计划的展示结构

任何时点只展示已创建的节点：

```text
L1 元问题
└── L2 子问题 A
    ├── 已回答：L3 子问题 A1
    └── 研究中：L3 子问题 A2
        ├── 已回答：L4 子问题 A2.1
        └── 待研究：L4 子问题 A2.2
```

每个终端节点旁边显示：需要的数据、分析方法、当前结论、充分性和下一步。
不要显示尚未由证据缺口触发的假想层级。

## 专业报告的文章化要求

当用户要求 HTML、正式报告或“券商级别”分析时，问题树只是导航，不能把节点
模型的字段逐项搬到页面后就视为完成。

### 统一阅读结构

使用仓库共享的 `question-tree-v1` HTML 模板：左侧问题树，右侧当前问题的研究文章。
每个节点的标题就是本层要回答的问题。正文模块严格按实际父子关系决定，不按 L 几决定：

- **非叶子节点**严格按三个模块排列：
  1. `研究子问题`：只列直接子问题，每题附一句 `why_it_matters` 并链接子章节，不嵌套整棵树。
  2. `子问题核心结论`：逐题列出直接子问题的核心结论、通过状态和边界，再综合说明它们如何回答父问题。
  3. `欠缺的方向`：列出本题及未充分子题的实质缺口、影响和下一步补证方向，并链接对应子题。
     没有重大缺口就明确说明，不为填满模块凭空新增问题；充分性与下一步归入本模块。
- **叶子节点**严格按三个模块排列：
  1. `核心观点`：直接回答当前问题，保留适用边界，不重复长篇论证。
  2. `关键论证`：用连续文章讲清关键事实如何支持观点、计算过程与反向解释；必要图表紧邻论证。
     充分性、关键未知与下一步在本模块末简短交代；补充测算也归入本模块，不增设第四模块。
  3. `数据列表`：列出本题实际使用的数据/事实、来源链接、日期、原文定位、作用与口径限制。
     没有证据时显示真实空状态，不用所需数据清单或待搜索材料充当已获数据。
- 三个模块是固定阅读结构，模块内不机械复制内部执行字段。`关键论证`仍需连续叙述，
  不是若干摘要或“一句话结论＋证据表”。
  数据比较、时间演化、情景敏感性确有需要且有数据时使用图表，标明单位、期间、来源、
  假设和计算方法；不为版式凑图或虚构数据。
- 来源紧邻事实，`数据列表`不代替正文。搜索计划、查询、解析和复核流水留在审计工件，
  不成为公共报告面板。上述结构适用于所有层级，包括 L1；由是否有真实子节点决定类型。

具体展示和验证规则以 `skills/value_invest_research/frameworks/research_report_contract.md`
为准。渲染器只呈现已有内容，不能生成分析、下钻理由或研究结论。

### 叶子节点

每个真正执行过材料搜集与分析的当前叶子节点，必须能够独立阅读为一篇研究章节：

1. 先用一两句直接回答问题，同时交代会改变答案的边界。研究对象和关键对照应清楚；
   不在开头堆期间、术语、通过标准和方法清单。
2. 展示决定结论的关键数据。数字旁边直接链接来源；衍生计算必须标明公式或推导，
   不得伪装成来源原值。
3. 用连续分析正文解释数据如何形成判断。正文至少处理因果机制、可比口径、
   替代解释以及支持证据与反向证据之间的关系。
4. 说明为什么相似指标不能相加或直接比较，以及这些限制影响的是方向、幅度还是
   兑现时间。
5. 结尾给出有边界的节点结论、剩余缺口、停止或继续下钻的理由，以及该结论如何
   回答父问题。

证据表用于审计，应保留来源、日期、原文位置、原子事实、作用方向和口径限制；
但证据表、流程步骤或若干 bullet 不能替代分析正文。未执行独立取证的节点不得
伪装成叶子研究章节。

### 父节点

父节点逐级汇总直接子节点，证据最终追溯到对应叶子，不越级平铺所有叶子或重复采集。
在“子问题核心结论”中列出可点击的直接子结论，再综合回答父问题，至少说明：

- 子结论如何首尾连接成父问题的因果链；
- 哪些子结论互相强化、互相制约或存在冲突；
- 近期与中长期判断为什么不同；
- 哪些剩余缺口会改变父结论，哪些只影响幅度或精度。

父结论不能只是拼接子结论，也不能因为所有子节点都“跑过”就自动通过。存在未通过
的必要子节点时，仍须列出该子问题及其有边界的暂时判断、状态和缺口，不能隐藏；
不得把暂时判断当作已验证结论。父节点只能报告为未充分，并明确下一执行节点。

### 读起来像论证，不像研究记录

写作前用一句话明确本题的主张，再选决定该主张的证据。推荐阅读顺序是
“直接答案 → 关键事实 → 为什么这些事实改变判断 → 能得出什么、还不能得出什么”。
这是论证顺序，不是强制四个标题；按问题复杂度决定篇幅，不以字数或小标题数量验收深度。

- 每段只推进一个判断，先说意思，再放数据，并解释数据意味着什么。段落之间说明因果、
  转折或条件关系，不连续罗列来源摘要。小标题写具体发现，不写“做出分析”等流程名。
- 主线优先保持一个对象、对照和任务口径。换案例前说明为什么需要它；不同模型、任务或
  期间的旁证不能替代本题的直接证据，更不能偷换父问题的对照。
- 数字交代“谁、什么单位、相对谁、有什么意义”。先用一个可复算的小例子讲清关系，
  再在必要时给通用公式和敏感性。专业名词首次用人话解释，不让符号先于经济含义出现。
- 假设紧贴算例，明确区分观测、推导、假设。“达到什么条件才成立”不等于“已经成立”；
  最强反证和影响结论的未知量必须在主文中可见，不能只藏在脚注、表格或折叠区。
- 次要案例、完整推导和重复的材料口径可放篇末补充分析。主文独立可读，但不删除原始证据、
  来源和审计记录；公共正文不重复研究步骤。具体呈现遵守报告契约。
- 父节点写子结论之间的关系及判断停在哪里，不重述每个子章节；重要的未通过分支在主文
  说明其影响。子结论清单与综合论证归入“子问题核心结论”，补证方向归入“欠缺的方向”。

发布前做一次读者复述检查：不打开补充材料，能否回答“目前知道什么、为什么支持这个
判断、还缺什么会让判断改变”？逐项与证据核对。表达不清先改稿；证据不够就保留缺口，
不得通过润色提升结论或充分性状态。结构校验通过不代表行文或研究质量通过。

## 运行纪律

- 默认从 L1 开始，完成问题设计审查后启动第一个可执行终端问题；在本仓库先建立必要的
  L1/L2/L3。用户只要求计划或修改 skill 时不启动取证。
- 任一时点明确一个“下一执行节点”，避免多个分支同时失去焦点。
- 子问题可以串行，也可以在真正独立时并行，但每个问题仍保持独立证据闭环。
- 用户修改元问题或边界时，追加范围变更事件；保留旧树，不静默重写历史。
- 遇到关键数据不可得时，输出阻塞原因和可执行的补证动作，不用模型先验填空。
- 研究报告只汇总已经通过充分性判断的结论；未通过节点作为缺口展示。

## 独立完成研究

本 skill 是唯一的投资研究入口，直接完成问题拆解、来源规划、材料解析、分析和汇总，
不依赖其它投资研究 skill，也不要求先安装一组专业技能。

- 财报：核对期间、单位、分部和现金流，区分实际值与管理层指引。
- 行业报告：提取模型、假设和预测口径，检验它是否真正回答当前问题。
- 新闻、会议和观点：区分官方事实、计划、预测和个人判断；未经验证的消息只作线索。
- 公司与估值：需要时验证业务敞口、盈利兑现和市场已计入的预期，不从主题相关性直接跳到推荐。
- 长材料：可使用已可用的阅读工具辅助提取，但逐题核对原文、反证和充分性的责任不转移。

这些是随当前问题选择的分析方法，不是必须逐项执行的固定清单。仓库既有的数据契约、
验证器和报告契约仍可复用；它们不构成额外 skill，也不替代本 skill 的动态研究循环。

## 禁止事项

- 不预先生成完整的 L2-L5 问题树。
- 不先搜集一大批材料，再把同一摘要映射到所有问题。
- 不因为找到若干相关资料就宣布节点完成。
- 不把“缺少资料”当作下钻理由；必须说明缺少哪个对象、指标、期间、机制或反证。
- 不让子问题偏离父问题的回答目标。
- 不用复杂术语、长问句或机械铺开的行业目录冒充研究深度；不把已有趋势直接当作事件增量。
- 不在达到最大深度后继续制造层级；应明确标记阻塞。
