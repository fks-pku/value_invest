# Dynamic Research Agent

把研究看成一棵边执行边生长的问题树，而不是一开始设计完整目录。

用户只需要提出一个 L1 元问题。研究 agent 负责逐层拆解、逐题取证、形成结论，
并根据答案是否充分决定停止当前分支，还是继续向下一层展开。

## 核心原则

1. **问题驱动**：每次搜集数据都服务于一个明确的当前问题。
2. **边研究边展开**：只生成回答当前父问题所必需的下一层子问题，不预先生成整棵树。
3. **逐子问题闭环**：每个子问题都经历“搜集数据 → 分析 → 结论 → 充分性判断”。
4. **缺口触发下钻**：只有答案不充分，而且能够说清缺少什么时，才继续展开。
5. **父问题由子结论汇总**：不能用未经验证的背景知识替代子问题结论。
6. **全程可追溯**：保留问题、来源、分析、结论、充分性判断和下钻原因。
7. **第一性原理，问题简洁**：从需求、资源消耗和关键约束解释结果；只保留能改变父问题判断的核心问题，不用术语或目录完整性代替思考。

## 问题设计：先找核心因果，再列问题

设计或修订问题树前，先用一句话说明用户要判断的结果，再写出解释该结果的最短
因果链。第一性原理不是抽象口号：要说清谁需要什么、为什么值得付费、实现它需要
什么资源、瓶颈在哪里，以及价值如何转成利润。按研究对象选择必要环节，不机械套全套清单。

- **从机制出发**：子问题对应因果链中尚需验证的关键环节，不从研报目录、热门概念、
  现成公司名单或已找到的材料倒推问题。Playbook 提供候选机制，不意味着全部展开。
- **做重要性筛选**：如果答案相反，会不会改变父结论的方向、规模、兑现时间或否决条件？
  若不会，就删去，或降为正文背景、数据口径；不要单独建节点。
- **一句人话，一个核心判断**：标题直接问“什么变了”“为什么多用”“谁能赚钱”等具体问题。
  公式、指标列表、地区和情景拆分放入 `data_required` 与 `analysis`，不要堆进问句。
  简洁的是问题，不是证据和分析的深度。
- **建立对照**：事件研究先核实事件是否发生、何时发生及可用范围；未确认就明确采用情景研究。
  比较“发生”与“未发生”的路径，不把原有行业增长全部归因于事件。
- **用可检验的桥梁连接环节**：必要时写量纲一致的关系式，区分任务量、算力用量、支出和利润；
  能力提升不等于付费需求，调用增加不等于算力支出增加，需求增长不等于供应商利润增长。
  每个关系中的关键假设都要能被证据推翻，公式本身不是证据。
- **先研究，再决定细分**：不凑固定问题数，不为每个指标或公司预建分支。
  反证先在本题处理；只有出现影响判断的具体缺口，才新增下一层问题。

### 示例：GPT-6 发布对 AI 行业的影响

以下是问题设计示意，不表示已经确认发布，也不是已经执行的研究计划。

L1：GPT-6 会怎样改变 AI 行业的需求和利润？主问题可围绕：

1. **它真正改变了什么？** 看能够可靠完成的新任务，以及完成同样任务的总成本；
   不只比较跑分或每 token 报价，总成本要考虑失败重试和人工复核。
2. **会带来多少真实需求？** 看哪些任务变得值得使用、客户愿意为此付多少钱；
   区分新增需求与替代已有模型或产品的使用。
3. **总算力需求会增加吗？** 同时检验任务量与每项任务的算力消耗，不能只看其中一项；
   从算力用量进一步推到采购支出时，还要处理利用率、存量容量和价格。
4. **新增利润会留在哪一环？** 看谁掌握难以替代的约束，以及竞争会不会把收益让给客户；
   不能从“受益于 AI”直接跳到公司利润。

只有需要作出证券投资决策时，再追问：**市场是否已把这些利润计入价格？**
其他题材应重建自己的因果链，不照搬本例。正式启动时按仓库约定先形成必要的 L1/L2/L3，
让每个 L3 直接进入取证；L4/L5 仍只由失败的充分性判断触发。

## 输入

启动研究时至少确认：

- `L1 元问题`：用户最终想知道什么。
- `研究边界`：对象、时间、地区、口径；用户没有给出时，采用最保守的明确假设。
- `完成标准`：什么样的答案足以支持用户的决策。
- `最大深度`：默认到 L5；到达 L5 仍不能回答时，记录为阻塞，不编造结论。

不要要求用户先设计 L2、L3。层级展开是 agent 的职责。

## 节点模型

问题树中的每个节点都使用同一结构：

```yaml
question_id: 稳定的问题编号
level: L1-L5
parent_id: 父问题编号；L1 为空
question: 这个节点要回答什么
why_it_matters: 它如何帮助回答父问题
status: pending | researching | answered | expanded | blocked
children: 已实际创建的直接子问题
conclusion: 当前结论
sufficiency:
  passed: true | false
  reasons: 为什么充分或不充分
  gaps: 仍缺少哪些证据、口径、对象或机制
```

每个当前终端节点还要保存：

```yaml
data_required: 需要搜集的数据
sources: 实际使用的来源及原文定位
analysis: 基于数据做了什么分析
supporting_evidence: 支持结论的证据
contrary_evidence: 反向证据或适用边界
next_action: 结束、继续搜集，或创建下一层子问题
```

## 研究循环

### 第一步：定义当前层要回答什么

对当前父节点明确写出：

- 本层问题。
- 它的回答边界。
- 什么结果算回答充分。

问题必须可以被证据回答，不能只是“了解一下”“分析行业”等宽泛表述。

### 第二步：生成最少量的直接子问题

先按“问题设计”规则筛掉不影响判断的分支，再列出回答当前节点所必需的直接子问题。每个子问题应当：

- 独立回答一个事实、比较、因果机制或反证。
- 能够通过具体数据或材料验证。
- 回答后可以直接贡献给父节点。
- 不与兄弟问题重复。

只展开一层。不要同时生成孙问题，也不要为了形式完整强行凑固定数量。

如果当前节点本身已经足够具体，可以直接研究它，不必机械拆分。

### 第三步：逐个研究子问题

对每一个当前终端子问题，严格执行以下闭环。

#### 3.1 收集数据

- 先写明需要哪些数据，再开始搜索。
- 每次搜索绑定当前问题编号。
- 优先使用原始资料、官方数据和可复核材料。
- 同时寻找支持材料与反向材料。
- 记录来源、发布日期、事实所属期间、口径和原文位置。
- 宽泛材料池只能提供候选，不能批量映射成多个问题的完成证据。
- 同一来源用于不同问题时，分别抽取和复核。

#### 3.2 做出分析

- 区分事实、推断和判断。
- 统一对象、单位、期间和统计口径。
- 解释数据如何回答当前问题，而不是只摘要材料。
- 比较支持证据、反向证据和替代解释。
- 明确不确定性来自数据缺失、口径冲突，还是机制尚未验证。

#### 3.3 得到结论

结论只回答当前子问题，至少包含：

- 一句话答案。
- 支持答案的关键证据。
- 反向证据或适用边界。
- 尚未解决的缺口。

没有证据支持的内容写成假设，不写成事实。

#### 3.4 判断回答是否充分

使用通过/不通过判断，不使用模糊的置信度分数。

只有同时满足以下条件，当前节点才算充分：

- 结论直接回答了问题。
- 核心事实具有可追溯来源。
- 对象、期间和口径足以支撑比较。
- 关键反向证据已经搜索并处理。
- 剩余缺口不会实质改变父问题的答案。

如果通过：

- 将节点标记为 `answered`。
- 停止该分支，不再增加层级。

如果不通过：

- 将节点标记为 `expanded` 或 `blocked`。
- 先写出具体缺口，例如“缺少 A 客户的当前部署数据”，而不是“资料不足”。
- 把每个实质缺口转换成最少量的下一层子问题。
- 每个新问题必须指明它关闭哪个缺口。
- 然后对新问题重复第三步。

### 第四步：汇总父节点

当所有必要子问题都已回答后：

1. 汇总子问题结论，形成父节点结论。
2. 再次判断父节点是否回答充分。
3. 若充分，关闭父节点并向上一层汇总。
4. 若仍不充分，识别遗漏维度或矛盾，只新增解决该缺口的直接子问题。

父节点不能因为“所有子问题都跑过”而自动完成；完成取决于答案是否充分。

## 循环伪代码

```text
research(node):
    明确 node 要回答什么，以及充分条件

    if node 足够具体且尚未研究:
        搜集数据(node)
        分析(node)
        形成结论(node)
        判断充分性(node)

    if node 回答充分:
        关闭 node
        return node.conclusion

    记录具体缺口

    if node.level == L5:
        标记 blocked
        return 未解决缺口

    仅按缺口创建下一层必要子问题

    for child in node.children:
        research(child)

    用子结论重新回答 node
    再次判断 node 是否充分
```

## 动态更新规则

每发生一个动作就追加一条事件，不覆盖历史：

- `question_created`
- `collection_started`
- `source_attached`
- `analysis_recorded`
- `conclusion_recorded`
- `sufficiency_evaluated`
- `question_expanded`
- `question_closed`
- `question_blocked`

动态计划展示的是事件账本投影出的当前状态。修改结论时保留旧结论及修改原因。

如果在文件型工作区运行，使用三个最小工件：

- `research_plan.md`：给人看的当前问题树和执行位置。
- `research_state.json`：当前节点、父子关系和充分性状态。
- `research_events.jsonl`：追加式事件与证据追踪。

不要为了归档方便再复制一套结论；结论只在状态和事件中有一个来源。

## 每轮输出格式

以下是内部执行记录或用户要求工作台时的格式，不是公共报告的文章模板。
普通汇报先给答案、关键依据及下一步；正式报告遵守下文的文章化要求。

```markdown
## 当前研究节点

- 层级与问题：L[n] · [问题]
- 父问题：[父问题]

### 数据

- [来源与关键事实]

### 分析

- [事实如何回答当前问题]
- [反向证据或边界]

### 结论

[只回答当前问题的一句话结论]

### 充分性判断

- 结果：通过 / 不通过
- 理由：[具体理由]
- 缺口：[具体缺口；没有则写“无重大缺口”]

### 动态计划更新

- 通过：关闭当前分支，返回父节点汇总。
- 不通过：新增 L[n+1] 子问题：[问题及其对应缺口]。
- 下一步：[唯一的下一执行节点]
```

## 研究计划的展示结构

任何时点只展示已创建的节点：

```text
L1 元问题
└── L2 子问题 A
    ├── 已回答：L3 子问题 A1
    └── 研究中：L3 子问题 A2
        ├── 已回答：L4 子问题 A2.1
        └── 待研究：L4 子问题 A2.2
```

每个终端节点旁边显示：需要的数据、分析方法、当前结论、充分性和下一步。
不要显示尚未由证据缺口触发的假想层级。

## 专业报告的文章化要求

当用户要求 HTML、正式报告或“券商级别”分析时，问题树只是导航，不能把节点
模型的字段逐项搬到页面后就视为完成。

### 统一阅读结构

使用仓库共享的 `question-tree-v1` HTML 模板：左侧问题树，右侧当前问题的研究文章。
每个节点的标题就是本层要回答的问题。正文模块严格按实际父子关系决定，不按 L 几决定：

- **非叶子节点**只有两个模块：`研究子问题`、`分析与结论`。
  前者只列直接子问题，每题附一句 `why_it_matters`，说明从哪个角度帮助回答父问题，
  并链接子章节；不嵌套整棵子树。后者用下层结论形成父问题的综合判断。
- **叶子节点**只有 `分析与结论`，不显示空的“研究子问题”或“无需展开”面板。
  这是一篇完整研究章节，不是“一句话结论＋证据表”。
- 正文按“核心判断 → 关键数据与推导 → 机制与反向解释 → 有边界的结论”组织连续叙述，
  可以有论点小标题，但不再机械拆成数据、分析、结论、充分性四个顶层模块。
  数据比较、时间演化、情景敏感性确有需要且有数据时使用图表，标明单位、期间、来源、
  假设和计算方法；不为版式凑图或虚构数据。
- 来源紧邻事实，详细证据表是补充，不代替正文。充分性、实质缺口和下一步放在篇末
  简短说明；搜索计划、查询、解析和复核流水留在审计工件，不成为公共报告面板。

具体展示和验证规则以 `skills/value_invest_research/frameworks/research_report_contract.md`
为准。渲染器只呈现已有内容，不能生成分析、下钻理由或研究结论。

### 叶子节点

每个真正执行过材料搜集与分析的当前叶子节点，必须能够独立阅读为一篇研究章节：

1. 先用一两句直接回答问题，同时交代会改变答案的边界。研究对象和关键对照应清楚；
   不在开头堆期间、术语、通过标准和方法清单。
2. 展示决定结论的关键数据。数字旁边直接链接来源；衍生计算必须标明公式或推导，
   不得伪装成来源原值。
3. 用连续分析正文解释数据如何形成判断。正文至少处理因果机制、可比口径、
   替代解释以及支持证据与反向证据之间的关系。
4. 说明为什么相似指标不能相加或直接比较，以及这些限制影响的是方向、幅度还是
   兑现时间。
5. 结尾给出有边界的节点结论、剩余缺口、停止或继续下钻的理由，以及该结论如何
   回答父问题。

证据表用于审计，应保留来源、日期、原文位置、原子事实、作用方向和口径限制；
但证据表、流程步骤或若干 bullet 不能替代分析正文。未执行独立取证的节点不得
伪装成叶子研究章节。

### 父节点

父节点逐级汇总直接子节点，证据最终追溯到对应叶子，不越级平铺所有叶子或重复采集。
在“分析与结论”中直接回答父问题，先写综合分析，再提供可点击的子结论依据，至少说明：

- 子结论如何首尾连接成父问题的因果链；
- 哪些子结论互相强化、互相制约或存在冲突；
- 近期与中长期判断为什么不同；
- 哪些剩余缺口会改变父结论，哪些只影响幅度或精度。

父结论不能只是拼接子结论，也不能因为所有子节点都“跑过”就自动通过。存在未通过
的必要子节点时，仍须列出该子问题及其有边界的暂时判断、状态和缺口，不能隐藏；
不得把暂时判断当作已验证结论。父节点只能报告为未充分，并明确下一执行节点。

### 读起来像论证，不像研究记录

写作前用一句话明确本题的主张，再选决定该主张的证据。推荐阅读顺序是
“直接答案 → 关键事实 → 为什么这些事实改变判断 → 能得出什么、还不能得出什么”。
这是论证顺序，不是强制四个标题；按问题复杂度决定篇幅，不以字数或小标题数量验收深度。

- 每段只推进一个判断，先说意思，再放数据，并解释数据意味着什么。段落之间说明因果、
  转折或条件关系，不连续罗列来源摘要。小标题写具体发现，不写“做出分析”等流程名。
- 主线优先保持一个对象、对照和任务口径。换案例前说明为什么需要它；不同模型、任务或
  期间的旁证不能替代本题的直接证据，更不能偷换父问题的对照。
- 数字交代“谁、什么单位、相对谁、有什么意义”。先用一个可复算的小例子讲清关系，
  再在必要时给通用公式和敏感性。专业名词首次用人话解释，不让符号先于经济含义出现。
- 假设紧贴算例，明确区分观测、推导、假设。“达到什么条件才成立”不等于“已经成立”；
  最强反证和影响结论的未知量必须在主文中可见，不能只藏在脚注、表格或折叠区。
- 次要案例、完整推导和重复的材料口径可放篇末补充分析。主文独立可读，但不删除原始证据、
  来源和审计记录；公共正文不重复研究步骤。具体呈现遵守报告契约。
- 父节点写子结论之间的关系及判断停在哪里，不重述每个子章节；重要的未通过分支在主文
  说明其影响，完整子结论清单放在综合论证之后。

发布前做一次读者复述检查：不打开补充材料，能否回答“目前知道什么、为什么支持这个
判断、还缺什么会让判断改变”？逐项与证据核对。表达不清先改稿；证据不够就保留缺口，
不得通过润色提升结论或充分性状态。结构校验通过不代表行文或研究质量通过。

## 运行纪律

- 默认从 L1 开始，并在同一轮创建必要的 L2 后启动第一个可执行子问题；除非用户只要求计划。
- 任一时点明确一个“下一执行节点”，避免多个分支同时失去焦点。
- 子问题可以串行，也可以在真正独立时并行，但每个问题仍保持独立证据闭环。
- 用户修改元问题或边界时，追加范围变更事件；保留旧树，不静默重写历史。
- 遇到关键数据不可得时，输出阻塞原因和可执行的补证动作，不用模型先验填空。
- 研究报告只汇总已经通过充分性判断的结论；未通过节点作为缺口展示。

## 独立完成研究

本 skill 是唯一的投资研究入口，直接完成问题拆解、来源规划、材料解析、分析和汇总，
不依赖其它投资研究 skill，也不要求先安装一组专业技能。

- 财报：核对期间、单位、分部和现金流，区分实际值与管理层指引。
- 行业报告：提取模型、假设和预测口径，检验它是否真正回答当前问题。
- 新闻、会议和观点：区分官方事实、计划、预测和个人判断；未经验证的消息只作线索。
- 公司与估值：需要时验证业务敞口、盈利兑现和市场已计入的预期，不从主题相关性直接跳到推荐。
- 长材料：可使用已可用的阅读工具辅助提取，但逐题核对原文、反证和充分性的责任不转移。

这些是随当前问题选择的分析方法，不是必须逐项执行的固定清单。仓库既有的数据契约、
验证器和报告契约仍可复用；它们不构成额外 skill，也不替代本 skill 的动态研究循环。

## 禁止事项

- 不预先生成完整的 L2-L5 问题树。
- 不先搜集一大批材料，再把同一摘要映射到所有问题。
- 不因为找到若干相关资料就宣布节点完成。
- 不把“缺少资料”当作下钻理由；必须说明缺少哪个对象、指标、期间、机制或反证。
- 不让子问题偏离父问题的回答目标。
- 不用复杂术语、长问句或机械铺开的行业目录冒充研究深度；不把已有趋势直接当作事件增量。
- 不在达到最大深度后继续制造层级；应明确标记阻塞。
