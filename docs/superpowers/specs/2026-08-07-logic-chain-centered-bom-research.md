# 以逻辑链为中心的 BOM 投资研究

> 状态：讨论基线，尚未实施
>
> 日期：2026-08-07
>
> 起点：GPU / ASIC BOM 需求侧报告迭代
>
> 适用范围：任何独立 BOM 节点的长期、滚动投资研究

## 1. 为什么需要改变研究中心

当前 GPU / ASIC BOM 需求侧研究暴露出一个根本问题：公开资料高度异构。
它们可能描述 GPU 数量、数据中心功率、资本开支、订单、Token、收入、市场规模、
公司规划或机构预测；对应时间可能是某个截点、一个期间、截至某年的累计值，
也可能只是长期方向。

如果把主要精力放在建立一张能够容纳所有信息的统一表格，就会出现两个问题：

1. 字段拆得越细，越难兼容新的信息形式；
2. 为了填满既有结构，容易把代理指标、场景假设和直接事实强行归一，制造伪精确。

因此，研究系统的中心不应是“信息如何被规范化”，而应是：

1. 基于第一性原理建立影响该 BOM 商业规模的逻辑链；
2. 把材料解析成出现在特定市场可见时点的原子观点；
3. 判断每条原子观点增强、削弱、限制或改变了逻辑链的哪个环节；
4. 在每个研究截面重建节点状态，再汇总为全局投资判断。

一句话模型：

```text
Source -> Atomic Claim -> Logic Impact -> Node State(t) -> Thesis Snapshot(t)
```

Q1、Q2、需求量矩阵、时间线和来源表都只是这套研究结构的派生视图，
不应成为底层研究本体。

## 2. 研究骨架：第一性原理逻辑链

面对任何一个 BOM，首先建立决定其商业规模和价值兑现的因果链。通用起点是：

```text
终端需求或工作负载
  -> 客户采用与支付意愿
  -> 主系统建设量
  -> 该 BOM 的渗透率或承接份额
  -> 单系统用量或价值量
  -> BOM 理论需求量
  -> 供给、认证和交付约束
  -> 实际出货与收入
  -> 毛利、现金流与盈利弹性
  -> 市场预期、估值和赔率
```

这不是所有 BOM 必须照抄的固定字段表，而是通用因果模板。每个 BOM 应根据自身
机制增删节点、分支和约束。

### 2.1 一个合格逻辑节点的定义

每个节点表达一条可验证、可反驳的因果命题，而不是一个宽泛主题。它至少说明：

- 当前主张是什么；
- 为什么它会影响下游；
- 可以观察哪些现象；
- 什么证据会削弱或推翻它；
- 它连接哪些上游和下游节点。

例如，GPU 需求研究中的逻辑节点可以是：

- AI 工作负载持续增长；
- 新增计算需求主要由 GPU 而不是替代加速器承接；
- 效率提升不足以抵消工作负载和计算强度增长；
- 客户预算和预期回报足以把理论需求转化为采购；
- 采购可以进一步转化为交付、上线、利用率和供应商收入；
- 上述增长尚未被市场完全定价。

### 2.2 逻辑链不是静态真理

第一性原理逻辑链是研究假设，不是永久不变的分类法。新信息可能：

1. 改变某个节点的状态；
2. 改变两个节点之间的传导关系；
3. 引入新的约束或替代分支；
4. 暴露原有逻辑链的边界错误。

逻辑链本身需要版本化。历史研究快照使用当时的逻辑链和当时可见的信息，
不能用今天新增的结构回写过去。

## 3. 原子化不等于字段化

原子化的目标是让一条观点只表达一个基本事实、预测或判断，并能追溯到原文。
它不意味着把观点继续拆成大量强制结构化字段。

例如：

> 某公司预计在 2028 年前建成 200MW 数据中心。

这是一条可以独立判断的原子观点。它不需要被强制换算为 GPU 数量，也不需要
为了进入统一表格而补造利用率、PUE、设备型号或采购进度。

### 3.1 原子观点的最小归档外壳

底层只强制保存保证审计和时序重建所需的最小信息：

- 原子观点原文；
- 来源及原文页码或章节；
- 市场何时能够知道，即 `published_at`；
- 信息性质，如事实、公司预期、第三方判断或市场消息；
- 所描述的期间：能够可靠解析时记录，无法解析时保留原始时间表述。

实体、指标、单位、目标期间、范围等可以在材料明确且研究确实需要时补充，
但不要求每条观点都填满同一个数据结构。

原则是：

> 观点拆得足够原子，字段保持足够克制，原始信息永不因映射需要而改写。

## 4. 核心账本：观点如何影响逻辑链

研究系统的主要结构应当是“观点与逻辑节点之间的关系”，而不是观点自身的
全方位标准化。

每条映射至少回答：

1. 这条观点主要影响哪个逻辑节点；
2. 它如何影响该节点；
3. 为什么产生这一影响；
4. 是否会继续影响下游节点；
5. 它是重复确认、真实新增还是与既有证据冲突；
6. 它是否揭示了逻辑链没有覆盖的新机制。

### 4.1 影响方式不能只有支持和反对

至少保留下列语义：

- 增强原有逻辑；
- 削弱原有逻辑；
- 改变适用边界；
- 引入新的约束；
- 引入新的逻辑分支；
- 与既有信息冲突；
- 暂时无法判断；
- 无法映射，进入新主题复核。

一条观点设置一个主要影响节点，同时可以记录辅助节点和下游影响。
“主要归属”用于避免重复解释，“辅助关系”用于保留真实的多重影响。

### 4.2 GPU 示例

| 原子观点 | 主要影响节点 | 影响方式 | 不应直接推出什么 |
|---|---|---|---|
| Token 调用量同比增长 21 倍 | 终端工作负载 | 增强 | 不能直接推出 GPU 同比增长 21 倍 |
| 推理效率提高 10 倍 | 单位工作负载所需算力 | 削弱或改变传导弹性 | 不能单独推出总 GPU 需求下降 |
| 云厂商上调资本开支 | 客户支付与建设能力 | 增强 | 不能假定全部资本开支用于 GPU |
| 计划建设 1GW 数据中心 | 主系统建设量 | 增强未来选项 | 不能当作已采购或已装机 GPU |
| 自研 ASIC 占比上升 | GPU 承接份额 | 削弱 | 不能脱离工作负载类型判断替代比例 |
| GPU 采购订单增长 | 理论需求向采购兑现 | 增强 | 不能直接当作当期上线和收入 |
| 交付延迟或利用率不足 | 采购向实际使用兑现 | 削弱 | 不能只因已有订单而忽略兑现风险 |

异构信息不必相互可比。只要能够审慎说明它影响了哪条因果命题，以及为什么，
它就能进入研究体系。

## 5. 时序研究：重建节点状态

原子观点按照市场可见时间追加。新材料不会直接重写当前结论，而是先形成一条
观点到逻辑节点的影响记录。

每个研究截面为每个节点生成状态，至少包括：

- 当前因果判断；
- 支撑该判断的关键原子观点；
- 削弱、限制或冲突的关键原子观点；
- 相较上一个真实截面的变化；
- 尚未解决的证据缺口；
- 下一步需要验证的观察项；
- 会推翻当前判断的反证条件。

节点状态不能通过简单统计支持和反对信息的数量形成。十篇转述同一消息的报告
不构成十份独立证据；一份直接、原始、可核验的材料可能改变整个节点判断。

### 5.1 观点时间与业务时间

研究演化的主轴是 `published_at`，即市场在什么时候第一次可以知道这条观点。
观点所描述的业务期间仍然保留，但它服务于理解观点内容，不用于强迫所有信息
进入同一时间序列表。

因此同一条观点同时回答两个不同问题：

- 它何时改变了市场可见的研究证据；
- 它描述的是当前事实、未来目标还是一个跨期规划。

## 6. 从节点状态形成全局投资判断

全局判断不是把所有材料汇总成一个大表，也不是把局部信息直接外推为投资结论。
它需要沿完整因果链检查传导是否成立。

例如，工作负载增长得到强化，并不自动等于 GPU 投资逻辑强化。还需要继续检查：

```text
工作负载增长
  -> 计算需求增长
  -> GPU 承接份额
  -> 效率和单位用量
  -> 客户预算
  -> 实际采购
  -> 交付和利用率
  -> 供应商收入和盈利
  -> 市场是否已经定价
```

任何关键承重节点断裂，最终投资判断都可能不成立。

每个全局研究快照应说明：

- 当前投资逻辑是什么；
- 哪些节点是核心承重节点；
- 哪些节点已经获得直接证据；
- 哪些节点仍依赖预测、代理信息或条件假设；
- 相较上一截面，哪条因果关系发生了真实变化；
- 哪些新信息没有改变核心判断；
- 哪些反证会触发判断降级。

## 7. 公开报告的呈现方式

公开报告不应再以大型信息表为主要叙事，而应采用三层结构。

### 第一层：全局逻辑链

展示影响 BOM 商业规模和投资价值的完整逻辑链。每个节点显示：

- 当前判断；
- 相较上一截面的变化；
- 关键约束或缺口。

读者首先看到的是投资逻辑在哪里成立、在哪里断裂，而不是材料数量。

### 第二层：节点的观点时间线

点击逻辑节点后，按市场可见时间展示影响该节点的原子观点：

```text
2026-03  原子观点 A -> 增强节点
2026-05  原子观点 B -> 引入边界条件
2026-07  原子观点 C -> 削弱节点
2026-08  节点判断发生修正
```

这些观点不要求单位一致，因为这里展示的是判断如何随信息演化，而不是伪造一条
可加总的数量曲线。

### 第三层：原始材料审计

点击观点后查看：

- 来源和链接；
- 发布日期；
- 原文位置；
- 原子观点；
- 映射理由；
- 对主要节点和下游逻辑的影响。

表格可以保留在这一层作为审计工具，但不再承担研究主叙事。

## 8. 对当前 Q1 / Q2 结构的影响

当前 GPU / ASIC 报告的 Q1 需求方和 Q2 需求量矩阵可以继续作为派生视图，
但不应再承担整个需求侧研究的底层结构。

后续迭代方向是：

1. 需求侧首先展示决定 GPU / ASIC 商业规模的第一性原理逻辑链；
2. 每个逻辑节点展示当前状态、真实变化和观点时间线；
3. Q1 需求方是“谁推动或承接需求”的局部视图；
4. Q2 当前数量是“已经兑现的数量证据”的局部视图；
5. 资本开支、电力、Token、订单和市场预测分别影响不同逻辑节点，
   不需要强行进入 Q2；
6. 最终需求判断从整条逻辑链的节点状态生成，而不是从 Q2 表格汇总生成；
7. 无法映射的观点保留为新主题，用于挑战或修订逻辑链。

## 9. 建议的内部工件

现有追加式账本可以沿用，但职责需要以逻辑链为中心重新确认：

```text
playbook / timeline_profile
  逻辑链、节点命题、上下游关系、观察项和反证条件

ledger/claims.jsonl
  最小归档外壳加不可变原子观点

ledger/claim_mappings.jsonl
  原子观点如何影响主要节点、辅助节点和下游逻辑

ledger/logic_states.jsonl
  每个研究截面的节点状态及相较上一截面的变化

ledger/thesis_revisions.jsonl
  哪些节点变化真正改变了全局投资逻辑

ledger/investment_snapshots.jsonl
  截至某个时点的完整投资判断、承重节点、缺口和反证条件
```

关键变化不是增加更多字段，而是让“观点影响逻辑节点”成为主关系，
让 Q1、Q2 和其他页面模块从节点状态派生。

## 10. 尚待下一轮确认的问题

这份文档只冻结讨论方向，不代表已经完成产品和代码设计。下一轮需要继续明确：

1. 通用 BOM 逻辑链的最小节点契约是什么；
2. 如何表达分支、约束、反馈和替代路线，而不是只支持线性链；
3. 逻辑链如何版本化，以及历史快照如何绑定链版本；
4. 一条原子观点主要映射一个节点、辅助映射多个节点时的审核规则；
5. 什么程度的节点变化才生成 thesis revision；
6. 如何避免模型仅凭措辞自动把观点升级为有效证据；
7. 当前 GPU / ASIC 数据如何迁移，而不改写既有原子观点；
8. HTML 中逻辑链、节点时间线和来源审计的具体交互设计；
9. Q1、Q2 是否继续作为公开命名，还是转为逻辑节点的派生视图；
10. 哪些现有框架契约、验证器和回归测试需要同步调整。

## 11. 本轮讨论形成的核心决定

> 不要建立“能够装下所有信息的表”；要建立“能够被任何信息挑战、增强、
> 削弱和修正的逻辑链”。

信息规范化只保留审计和时序重建所必需的最小外壳。研究工作的中心是逻辑链的
合理性、原子观点对各节点的影响，以及由节点状态形成的全局投资判断。
